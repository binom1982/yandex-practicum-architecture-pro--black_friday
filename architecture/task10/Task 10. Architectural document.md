# Задание 10. Миграция на Cassandra

## 10.1 Критические сущности для Cassandra

**Выбранные сущности:**

1. **Пользовательские сессии:** Высокая частота записи/обновления, TTL-данные.

   * Сессия имеет естественный срок жизни (например, 24–48 часов неактивности).
   * Cassandra поддерживает `TTL` на уровне записи:

   ```sql
     INSERT INTO sessions (session_id, data) 
     VALUES (...) USING TTL 86400; -- 24 часа
   ```
2. **Корзины покупок:** Высокая запись, eventual consistency допустима.
3. **История заказов:** Write-heavy, доступ преимущественно по `user_id`.

   * Cassandara архитектурно оптимизирована для задач Write-heavy (операций записи значительно больше, чем чтения)

**Обоснование:**

* **Масштабируемость:** Cassandra обеспечивает линейное масштабирование записи (leaderless), что критично при 50k req/sec.
* **Геораспределённость:**  репликация между несколькими дата-центрами обеспечивает доступность при падении дата-центра.
* **Целостность:** Для этих сущностей допустима eventual consistency (в отличие от финансовых транзакций или остатков товаров, которые остаются в SQL/ACID БД).
* **Проблема MongoDB:** Cassandra использует consistent hashing, а не range-based sharding. Добавление ноды затрагивает только соседние токены, исключая полный ребаланс данных и просадки latency.

## 10.2 Концептуальная модель данных

### Модель сущностей и ключи

**1. Пользовательские сессии**

* **Partition Key:**`session_id` (UUID).
* **Clustering Key:** Отсутствует.
* **Обоснование:** UUID обеспечивает случайное хеширование, гарантируя равномерное распределение сессий по узлам кластера. Доступ осуществляется точечным запросом по ID (O(1)), что критично для валидации сессии на каждом запросе.

**2. Корзины покупок**

* **Partition Key:**`owner_id` (UUID).
* **Clustering Key:** Отсутствует (данные товаров хранятся внутри записи как коллекция).
* **Обоснование:** Все данные корзины пользователя находятся в одной партиции на одном узле. Это позволяет читать и обновлять корзину за один сетевой запрос. UUID предотвращает скопление данных популярных пользователей на одном узле (если ID не последовательные).

**3. История заказов**

* **Partition Key:**`user_id` (UUID).
* **Clustering Key:**`order_date` (TIMESTAMP), `order_id` (UUID).
* **Обоснование:** Группировка по пользователю позволяет быстро выгружать историю. Сортировка по дате внутри партиции позволяет получать последние заказы через `LIMIT` без дорогостоящей сортировки на уровне приложения.

### Обоснование выбора модели

**Равномерное распределение и доступ**

* Использование **UUID** в качестве Partition Key исключает последовательные закономерности. Хеш-функция Cassandra равномерно разбрасывает токены по кольцу, предотвращая дисбаланс нагрузки между узлами.
* Clustering Key в истории заказов обеспечивает физическую сортировку данных на диске. Это позволяет выполнять диапазонные запросы (например, «заказы за месяц») чтением непрерывного блока данных, минимизируя I/O операции.

**Горячие партиции (Hot Partitions)**

* **Риск:** Если один `user_id` генерирует аномально высокую нагрузку (бот-атака), узел, хранящий эту партицию, может перегрузиться.
* **Минимизация:** Случайность UUID снижает вероятность естественного возникновения горячих точек. Для искусственных атак применяются механизмы Rate Limiting на уровне приложения или балансировщика, так как изменение схемы данных не защитит от целевой атаки на конкретный ID.

**Влияние решардинга (Масштабирование)**

* **Механизм:** Cassandra использует **consistent hashing** (виртуальные узлы/vnodes), а не диапазонное шардирование как MongoDB.
* **Эффект:** При добавлении нового узла он забирает часть токенового диапазона только у **соседних** узлов. Не происходит полного перераспределения данных между всеми узлами кластера.
* **Результат:** Операция масштабирования не вызывает глобального скачка latency и доступна во время пиковых нагрузок, так как миграция данных происходит фоново и локально.

## 10.3 Стратегии обеспечения целостности

| **Стратегия** | **Сущности**    | **Обоснование**                                                                                                                                                                                                                                                                        |
| ---------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hinted Handoff               | Все                        | Включено по умолчанию. Позволяет принимать запись на живую ноду, если целевая недоступна. Критично для доступности во время пиков.                                                         |
| Read Repair                  | Сессии, Корзины  | Данные читаются часто. Проверка и синхронизация реплик при чтении обеспечивают актуальность без фоновых затрат. Компромисс: минимальное увеличение latency чтения. |
| Anti-Entropy (Repair)        | История заказов | Чтение реже, запись объемная. Фоновый процесс (NodeSync) гарантирует конечную согласованность без влияния на latency пользовательских запросов.                                             |

**Уровень согласованности (Consistency Level):**

* **Write/Read: QUORUM.** Гарантирует, что данные прочитаны/записаны на большинстве реплик. Баланс между надежностью и скоростью. Для некритичных данных (логи) возможно `ONE`.
