# Архитектурный документ: Стратегия хранения и шардирования данных

## 1. Обзор архитектурных решений

Гибридная архитектура хранения данных для обеспечения масштабируемости и отказоустойчивости.

| **Система** | **Назначение**                                                          | **Обоснование**                                                                                                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MongoDB (Sharded)        | Товары (`products`), Активные заказы (`orders`), Остатки | Транзакционная целостность (ACID), гибкая схема,<br />шардирование для горизонтального масштабирования записи. |
| Cassandra                | Сессии, Корзины (`carts`), История заказов                 | Write-heavy нагрузка, линейное масштабирование,<br />TTL для сессий, eventual consistency допустима.                                                 |

## 2. Структуры данных и ключи шардирования

**MongoDB Коллекции**

| **Коллекция** | **Shard Key**   | **Тип** | **Обоснование**                                                                                 | **Риски**                                                                    |
| ---------------------------- | --------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `orders`                   | customer_id (Hashed) | UUID             | Все заказы пользователя в одном шарде. Быстрый поиск истории. | Scatter-Gather при аналитике.                                               |
| `products`                 | product_id (Hashed)  | UUID             | Равномерное распределение. Эффективное списание остатков.     | Поиск по категориям требует опроса всех шардов. |

**Cassandra Таблицы (Миграция)**

| **Таблица** | **Partition Key** | **Clustering Key**     | **Обоснование**                                                                                                      |
| ------------------------ | ----------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `sessions`             | session_id(UUID)        | -                            | Равномерное распределение. Доступ O(1). TTL 24-48ч.                                                    |
| `carts`                | owner_id(UUID)          | -                            | Все товары корзины в одной партиции. Обновление за 1 запрос.                          |
| `order_history`        | user_id(UUID)           | `order_date`,` order_id` | Группировка по пользователю. Сортировка на диске для выборок по времени. |

## 3. Конфигурация и примеры команд

**MongoDB Шардирование**

```bash
// Включение шардирования для БД
sh.enableSharding("ecommerce");

// Шардирование коллекции orders (Hashed)
sh.shardCollection("ecommerce.orders", { customer_id: "hashed" });

// Проверка баланса
sh.status();
```

**Cassandra Запросы и Настройки**

```sql
-- Сессии с TTL
INSERT INTO sessions (session_id, data) 
VALUES (uuid(), ...) USING TTL 86400;

-- Уровень согласованности
CONSISTENCY QUORUM; 
-- Баланс между надежностью и скоростью (запись/чтение на большинстве реплик)
```

**Стратегия чтения (MongoDB)**

| **Коллекция** | **Операция**                                                   | **Источник чтения** | **Обоснование**                                                                                                                          |
| ---------------------------- | ---------------------------------------------------------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| products                     | Просмотр каталога, поиск, карточка товара | Secondary                               | Допустима временная неактуальность (цена, описание). Снижение нагрузки на Primary.          |
| products                     | Проверка остатков (перед оплатой)                | Primary                                 | Критично избежать оверселлинга. Требуется строгая консистентность.                             |
| orders                       | История заказов (список)                                 | Secondary                               | Допустима задержка отображения архивных данных.                                                                 |
| orders                       | Статус заказа (сразу после действия)           | Primary                                 | Пользователь ожидает мгновенного отражения изменения состояния.                                  |
| carts                        | Просмотр, добавление, удаление товаров      | Primary                                 | Высокая частота изменений. Риск рассинхронизации данных внутри сессии пользовател |

## 4. Мониторинг и эксплуатация

**Ключевые метрики (MongoDB)**

| **Метрика**   | **Порог алерта**     | **Действие**                                                                                 |
| -------------------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `ops/sec`(на шард) | Отклонение > 20%            | Проверка распределения ключей, запуск балансировщика.       |
| `mem_resident`           | Высокое потребление | Анализ индексов, возможное вертикальное масштабирование. |
| `global_lock_queue`      | Рост очереди               | Оптимизация запросов, проверка горячих шардов.                     |

**Управление целостностью и инцидентами**

| **Проблема**                     | **Стратегия уменьшения рисков**                                                                                                                                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Горячие шарды                      | Использование `hashed` ключей.<br />Кэширование популярных категорий (Redis).<br />Команда `reshardCollection` (в окно низкой нагрузки).        |
| Несогласованность (Cassandra) | **Hinted Handoff** (доступность при падении нод)<br />**Read Repair** (для сессий/корзин).<br />**Anti-Entropy** (фоновый ремонт для истории). |
| Неизменяемость ключа        | Тщательный анализ ключей перед продакшеном. Миграция данных требуется для смены ключа.                                                               |
