### Логика принятия решений

1. **Коллекция orders (Ключ: `customer_id`, Hashed):**
   * Шардирование по customer_id, для того, чтобы все заказы одного пользователя попали в один шард, чтобы исключить опрос всех шардов. Необходимо для быстрого поиска истории заказов конкретного пользователя.
   * Хеширование удовлетворяет P-2 , распределяя клиентов равномерно по шардам
2. **Коллекция products (Ключ: `product_id`, Hashed):**
   * Шардирование по product_id, чтобы все товары попадали в один шард для эффективного списания остатков
   * Необходимо для быстрого просмотра товара
   * Для "Поиск товаров по категориям и фильтрация по диапазону цен" будет необходимо опрашивать все шарды, тк по полям category и price нет шардирования
3. **Коллекция carts (Ключ: `owner_id`, Hashed):**
   * Шардирование по owner_id - унификация доступа для гостей и пользователей
   * Добавление/замена/удаление товара в корзине, все данные на одном шарде
4. **Соблюдение ограничений:**
   * Выбор неизменяемых полей в качестве ключей учитывает ограничение +R-1
   * Индексы строятся с учетом ограничения +R-2

## **Альтернативы**

1. **Коллекция orders, шардирование по времени (`created_at`):**

   * *Плюсы:* Удобно для выборки последних заказов и архивации.
   * *Минусы:* Нарушает  P-2. Все новые записи идут на один шард, создавая bottleneck на записи.
2. **Коллекция orders, шардирование по геозоне (`geo_zone`):**

   * *Плюсы:* Локальность для логистики.
   * *Минусы:* Нарушает  P-2. Крупные города создадут огромные шарды. Заказы могут содержать товары из разных зон, усложняя **транзакции.**
3. **Единый ReplicaSet (без шардирования):**

   * *Плюсы:* Простота разработки, нет ограничений  +R-1, +R-2 .
   * *Минусы:* Нарушает  P-1. Вертикальное масштабирование имеет предел.

### Недостатки, ограничения, риски

1. **Scatter-Gather запросы (Производительность):**
   * *Риск:* Поиск товаров по категории **( UC-3 ) требует опроса всех шардов, что увеличивает задержку.**
   * *Митигация:* Внедрение кэширования каталога (Redis) и направление поисковых запросов только на Secondary реплики.
2. **Неизменяемость шард-ключа (Ограничение +R-1):**
   * *Риск:* Если бизнес-логика изменится, миграция данных будет сложной операцией.
   * *Митигация:* Тщательный анализ требований перед продакшеном. Использование абстракции `owner_id` в корзинах.
3. **Уникальность данных (Ограничение +R-2):**
   * *Риск:* Невозможно создать уникальный индекс на поле, не входящее в шард-ключ.
   * *Митигация:* Гарантировать уникальность на уровне приложения или включать шард-ключ в состав уникального индекса.
4. **Сложность транзакций (Надежность R-1):**
   * *Риск:* Транзакции между шардами снижают производительность.
   * *Митигация:* Denormalization. В документ заказа копируются данные о товаре. Списывание остатков делается в рамках одного документа товара.
